# Architecture

## System Overview

Robusta is a fast, Rust-native Java formatter and linter. One native binary owns source discovery, configuration, parsing, formatting, linting, fixes, diagnostics, and machine-readable reports. Build-tool integrations remain thin adapters around that binary: they select CLI modes and never reimplement its work.

### Core Mission

- **Performance**: Deliver native-speed formatting and linting without a JVM startup penalty
- **Correctness**: Preserve parse success, idempotency, and the significant token stream on every formatting path
- **Determinism**: Produce identical bytes from a parallel run and a single-threaded run
- **Developer Experience**: Provide one CLI, one configuration format for formatting and linting, and reports that both humans and CI can read

## Architecture Principles

### 1. Arena-Per-File Architecture

Parser-owned AST nodes and collections are allocated in `robusta_allocator`. Each processed file takes an arena from the run's pool, which resets it as a unit for the next file, so allocation is a pointer bump, nodes land next to each other in memory, and no reference counting is needed in hot paths.

### 2. Visitor Pattern

AST traversal is implemented using the visitor pattern (`robusta_ast_visit`). `tasks/ast_tools` generates the per-type traversal from the `#[ast(visit)]` types, which declare their children in source order.

### 3. Shared Infrastructure

Common functionality like error reporting (`robusta_diagnostics`), source positions (`robusta_span`), and Javadoc recognition (`robusta_javadoc`) is shared across all components to ensure consistency.

## Core Components

### Foundation Layer

#### robusta_allocator

- **Purpose**: Per-file bump allocation and arena-backed collections
- **Key Features**:
  - One arena per processed file, reused across a run
  - Pointer-bump node allocation
  - No reference counting in hot paths
- **Dependencies**: `robusta_data_structures`

#### robusta_span

- **Purpose**: Source position tracking
- **Key Features**:
  - Half-open byte spans into the source
  - Positions derived only for presentation
  - Labeled diagnostic spans
  - Content comparison that ignores source positions
- **Dependencies**: `robusta_allocator`, `robusta_ast_macros`

#### robusta_syntax

- **Purpose**: Java syntax vocabulary beneath the AST
- **Key Features**:
  - Operator definitions
  - Identifier, whitespace, and line terminator character classes
  - Line helpers
  - Node, scope, symbol, and reference index types
  - Usable without depending on the tree
- **Dependencies**: `robusta_ast_macros`, `robusta_span`

#### robusta_ast

- **Purpose**: Arena-allocated typed Java AST and generated node kinds
- **Key Features**:
  - `CompilationUnit` root owning file comments
  - Comments held outside the tree
  - Memory layout checked at compile time
- **Dependencies**: `robusta_allocator`, `robusta_ast_macros`, `robusta_span`, `robusta_syntax`

#### robusta_ast_macros

- **Purpose**: The `#[ast]` attribute on every AST type
- **Key Features**:
  - Predictable memory layout, with `repr` and the field order `tasks/ast_tools` calculates
  - Checks that the traits named by `#[generate_derive]` are in scope
- **Dependencies**: None (proc-macro)

#### robusta_ast_visit

- **Purpose**: Read-only AST visitor traits and generated traversal
- **Key Features**:
  - Per-type traversal generated by `tasks/ast_tools`
  - Source-order traversal
  - Scope entry and exit placed by `#[scope]` markers
  - Comments skipped by traversal
- **Dependencies**: `robusta_allocator`, `robusta_ast`, `robusta_syntax`

#### robusta_diagnostics

- **Purpose**: Diagnostic protocol, graphical renderer, and output routing
- **Key Features**:
  - One protocol for every diagnostic producer
  - Graphical renderer for human reports
  - Fallible stdout and stderr writers
- **Dependencies**: `robusta_span`, `robusta_syntax`

### Core Processing Layer

#### robusta_config

- **Purpose**: Configuration discovery, file selection, and directory walking
- **Key Features**:
  - Nearest `robusta.yaml` per Java file, covering formatting and linting
  - Glob patterns for `overrides` and gitignore patterns for `ignore-patterns`
- **Dependencies**: None (workspace-internal)

#### robusta_lexer

- **Purpose**: Whole-file Java tokenization and lexical diagnostics
- **Key Features**:
  - Whole-file tokenization before parsing
  - Separate flat token and comment buffers
  - Sparse decoded identifier names
  - Token recognition only, no grammar
- **Dependencies**: `robusta_ast`, `robusta_span`, `robusta_syntax`, `robusta_diagnostics`

#### robusta_parser

- **Purpose**: Java grammar, recursive-descent parsing, and recovery
- **Key Features**:
  - Hand-written recursive descent parser
  - Finalized Java syntax through Java 25
  - Contextual keywords resolved by position
  - `Clean`, `Recovered`, and `Fatal` outcomes
- **Dependencies**: `robusta_lexer`, `robusta_ast`, `robusta_allocator`, `robusta_diagnostics`, `robusta_span`, `robusta_syntax`

#### robusta_javadoc

- **Purpose**: Shared Javadoc recognition, structure, tags, and references
- **Key Features**:
  - Javadoc structure and tag model
  - Reference parsing for downstream consumers
- **Dependencies**: `robusta_ast`, `robusta_lexer`, `robusta_span`, `robusta_syntax`

#### robusta_semantic

- **Purpose**: Flattened nodes and file-local scopes, symbols, and references
- **Key Features**:
  - One preorder traversal per compilation unit
  - Flattened AST nodes with parent links
  - Arena-owned relationship indexes
  - Analysis bounded by the compilation unit
- **Dependencies**: `robusta_ast`, `robusta_ast_visit`, `robusta_allocator`, `robusta_javadoc`, `robusta_span`, `robusta_str`, `robusta_syntax`

#### robusta_formatter_core

- **Purpose**: Language-agnostic formatting representation and width-driven printer
- **Key Features**:
  - Flat element stream for text and breaks
  - Group layout measured against line width
  - No language-specific policy
- **Dependencies**: `robusta_allocator`, `robusta_data_structures`, `robusta_span`

#### robusta_formatter

- **Purpose**: Java formatting and trivia policy
- **Key Features**:
  - Java syntax, comment, and import policy
  - Generated per-node printing, with each node's comments found by source position
  - Shared vertical and fill list layout
  - One element stream for all output
- **Dependencies**: `robusta_formatter_core`, `robusta_parser`, `robusta_ast`, `robusta_ast_visit`, `robusta_javadoc`, `robusta_lexer`, `robusta_diagnostics`, `robusta_allocator`, `robusta_span`, `robusta_syntax`

#### robusta_linter

- **Purpose**: Rule coordination, suppressions, and classified text-edit fixes
- **Key Features**:
  - Rules configured once per resolved config
  - Dispatch bucketed by AST node kind
  - Non-overlapping span replacements
  - Two-axis fix classification
- **Dependencies**: `robusta_semantic`, `robusta_ast`, `robusta_config`, `robusta_diagnostics`, `robusta_macros`, `robusta_allocator`, `robusta_span`, `robusta_syntax`

### Application Layer

#### robusta CLI (apps/robusta)

- **Purpose**: The native `robusta` executable
- **Key Features**:
  - Verbs `check`, `format`, `lint`, `init`, and `config`
  - Command-specific execution variants
  - Parallel processing with input-order results
  - `.editorconfig` fallback for omitted formatter values
  - One terminal-outcome to exit-code mapping
- **Dependencies**: All core components

#### Gradle Plugin (jvm/gradle-plugin)

- **Purpose**: Java 8 Gradle adapter that resolves, extracts, and invokes the native executable
- **Key Features**:
  - The running platform's executable, resolved from the plugin repositories
  - Configuration-cache compatible tasks
- **Dependencies**: `jvm/common`

#### Maven Plugin (jvm/maven-plugin)

- **Purpose**: Java 8 Maven adapter over the same command surface
- **Key Features**:
  - One goal per fixed Gradle task
  - The running platform's executable, resolved from the plugin repositories
- **Dependencies**: `jvm/common`

## Data Flow

### Compilation Pipeline

1. **Input**: Java source + `robusta.yaml` + `.editorconfig` fallbacks
2. **Discovery**: Configuration resolution and file selection
3. **Lexing/Parsing**: `robusta_lexer` → `robusta_parser` → typed AST + comments
4. **Formatting**: `robusta_formatter` → formatting IR → printer, working from the parsed AST
5. **Linting**: `robusta_semantic` → flattened nodes, scopes, symbols, references → `robusta_linter` rules, built only for runs that lint
6. **Output**: Diagnostics and text edits, reported in input order

### Memory Management Flow

```
Source Text → Arena Allocator → AST Nodes → Visitors → Results
     ↓              ↓              ↓           ↓          ↓
   UTF-8         Per-file       Borrowed     Shared     Owned
   Bytes          Arena        References   Traversal   Output
```

## Quality Attributes

### Performance

- **Target**: Faster than the established Java formatters, with no JVM startup cost
- **Strategies**:
  - One arena per file for parser-owned nodes, reused across a run
  - File-level parallelism with deterministic ordering
  - No repeated parsing in common paths
  - Dedicated pipeline time and allocation tracking tasks

#### Parser Performance Implementation

- The whole file is tokenized once, before parsing
- AST is allocated in a memory arena (`robusta_allocator`) for fast allocation and deallocation

#### Linter Performance Implementation

- Semantic analysis performs one shared preorder traversal; rules never walk the AST independently
- Each AST node is dispatched only to rules that declare an interest in that node kind

### Correctness

- **Target**: Preserve source meaning on every transforming path
- **Strategies**:
  - Grammar, diagnostic, and recovery tests
  - Exact output, idempotency, and comment preservation tests
  - Fix safety, suppression, and floor tests
  - Routing, exit status, and report tests
  - Corpus invariant tasks

### Maintainability

- **Target**: One owner for every policy decision
- **Strategies**:
  - No Java policy inside `robusta_formatter_core`
  - One formatting representation and one printer path
  - One registry for every built-in rule

### Usability

- **Target**: Readable by a developer and a CI job alike
- **Strategies**:
  - The report on stdout, or on stderr when stdout carries a document
  - Exit status independent of output verbosity
  - Preview flags that report without writing

## Technical Constraints

### Language Choice

- **Rust**: Chosen for native speed and single-binary distribution

### Memory Model

- **Arena Allocation**: One arena per processed file, reset as a unit for the next
- **Span Representation**: Half-open byte ranges into the original source
- **Position Derivation**: Line and column computed only when presenting diagnostics

### Threading Model

- **File-level Parallelism**: Each file processed independently
- **Deterministic Output**: Results emitted in input order
- **Run Equivalence**: Parallel and single-threaded runs produce identical bytes

### Compatibility Requirements

- **Java Syntax**: Finalized releases through Java 25; preview features excluded
- **Clean Parse**: Recovered source is reported, never transformed
- **Source Level**: Built-in fixes preserve the Java 8 floor
- **Formatter Parity**: Byte-identical output from another formatter is not a goal

## Design Decisions

### Arena Allocator Choice

**Decision**: Use a per-file arena instead of reference counting
**Rationale**:

- A file is the unit of work, matching what one arena holds
- Allocating a node is a pointer bump, not a system allocator request
- Nodes land next to each other in memory
- The whole arena is reset for the next file when the file is done

### Hand-written Parser

**Decision**: Implement recursive descent over a pre-tokenized stream instead of a parser generator
**Rationale**:

- Grammar ambiguities are resolved by position
- Contextual words keep parsing as identifiers
- Recovery behavior is explicit at each site

### Comments Outside the Tree

**Decision**: Keep comments on the `CompilationUnit` root rather than in AST nodes
**Rationale**:

- An AST holds only what is semantically relevant
- Visitor traversal is not burdened with trivia
- Each node's generated printer prints the comments before and after it, found by source position
- Blank lines are restored by counting line terminators between spans

### Two-Axis Fix Classification

**Decision**: Classify a fix by action and risk instead of a single tier
**Rationale**:

- A command names the kinds it permits, not a tier including everything beneath it
- Action and risk vary independently in practice

## Future Considerations

### Planned Extensions

- **Formatter Coverage**: Continued expansion of formatting policy
- **Rule Set**: More sound file-local lint rules
- **Distribution**: Complete build-tool delivery

### Scalability Concerns

- **Whole-program Analysis**: Outside scope; stays with SonarQube, Error Prone, and SpotBugs

### Technology Evolution

- **Java Releases**: The parser tracks finalized releases
- **Preview Features**: Admitted only once finalized

## Development Infrastructure

### Test Infrastructure

Repository task crates provide focused quality gates:

- **Conformance**: Java source-level compilation checks for built-in fixes
- **Coverage**: Corpus parsing, formatter idempotency, and token and comment preservation
- **AST Tools**: Generated node kinds, traversal, and formatter node wrappers with committed-artifact drift checks

### Build and Development Tools

- **Benchmark**: Criterion benchmarks for individual stages and the full pipeline
- **Track Memory Allocations**: Deterministic arena-growth measurements by pipeline stage
- **Website**: `robusta.schema.json` with its drift check, and CLI and configuration reference pages generated from the argument parser and schema
- **Just**: `just ready` runs the local Rust gate; `just deny` adds licensing and advisory gates, and CI adds the plugin, conformance, MSRV, unused-dependency, and cross-platform jobs
